Ты работаешь в пустом Git-репозитории. Нужно самостоятельно спроектировать и реализовать полностью рабочую первую версию Telegram-бота для автоматического поиска быстрорастущих русскоязычных TikTok-нарезок из фильмов и сериалов.

Не ограничивайся созданием каркаса проекта. Доведи приложение до состояния, которое можно клонировать на Ubuntu 24.04, настроить через `.env`, запустить как systemd-сервис и использовать.

Если конкретная внешняя интеграция или библиотека изменилась, исследуй актуальное состояние и выбери рабочий бесплатный вариант. Не используй платные API и не делай платные сервисы обязательными.

## 1. Назначение приложения

Бот нужен для личного использования и небольшой группы людей, которым известен общий пароль.

Основной сценарий:

1. приложение постоянно ищет в TikTok свежие русскоязычные ролики с нарезками фильмов и сериалов;
2. отслеживает изменение их статистики;
3. определяет, какие ролики растут быстрее остальных;
4. каждые 3 часа выбирает TOP-3;
5. скачивает только эти три ролика;
6. пытается определить фильм или сериал;
7. отправляет подписчикам Telegram:
   - MP4;
   - ссылку на оригинальный TikTok;
   - показатели ролика;
   - скорость роста;
   - автора;
   - возраст публикации;
   - Trend Score;
   - предполагаемый источник: название фильма или сериала;
8. хранит скачанный MP4 максимум 6 часов;
9. затем автоматически удаляет файл.

Главная цель не просто находить самые популярные TikTok, а находить ролики, которые прямо сейчас быстро набирают просмотры.

## 2. Ограничения

Сервер:

- Ubuntu 24.04;
- 2 AMD EPYC CPU cores;
- 2 GB RAM;
- 50 GB disk;
- без GPU.

Проект должен быть рассчитан на эти ресурсы.

Не использовать тяжелые постоянно работающие ML-модели.

Допускаются:

- бесплатные сторонние API;
- бесплатные API tiers;
- open-source библиотеки;
- scraping публично доступных страниц;
- Playwright;
- yt-dlp;
- другие бесплатные источники.

Но:

- никаких обязательных платных API;
- никакого автоматического перехода на платный тариф;
- приложение должно продолжать основную работу, если необязательный внешний сервис недоступен;
- внешние интеграции должны быть заменяемыми;
- не реализовывать обход CAPTCHA, авторизации, технических ограничений платформы или иные механизмы агрессивного anti-bot bypass.

## 3. Архитектура TikTok provider

Не связывай бизнес-логику напрямую с конкретным scraper/API.

Создай абстракцию примерно такого смысла:

`TikTokProvider`

Она должна уметь:

- искать ролики по запросу/хэштегу;
- получать metadata видео;
- получать текущие счетчики;
- получать автора и, если возможно, число его подписчиков;
- получать дату публикации;
- отдавать URL;
- скачивать видео либо предоставлять URL для downloader.

Бизнес-логика ranking не должна знать, используется ли внутри:

- scraper;
- API;
- Playwright;
- yt-dlp;
- иной источник.

Нужно реализовать как минимум один реально рабочий бесплатный provider для первой версии.

Если целесообразно, сделай fallback provider.

В README подробно объясни ограничения выбранного способа получения TikTok-данных.

## 4. Поисковые запросы

Начальный постоянный список примерно такой:

- фильм
- фильмы
- сериал
- сериалы
- кино
- нарезка
- нарезка из фильма
- момент из фильма
- момент из сериала
- лучшие моменты
- #фильм
- #фильмы
- #сериал
- #сериалы
- #кино
- #нарезка

Храни базовые запросы в конфиге проекта, а не хардкодь по разным модулям.

Конкретные названия фильмов вручную добавлять не требуется.

## 5. Автоматическое расширение запросов

Бот должен анализировать хэштеги найденных подходящих роликов.

Если появляется перспективный новый русскоязычный хэштег/поисковый запрос, бот НЕ должен добавлять его автоматически.

Вместо этого всем авторизованным пользователям отправляется предложение:

`Предлагаю добавить поисковый запрос: #пример`

Inline-кнопки:

`✅ Добавить`
`❌ Отклонить`

Первое принятое решение считается итоговым.

После решения остальные кнопки должны стать неактуальными или сообщение должно обновиться соответствующим образом.

Одобренный динамический запрос:

- активен 24 часа;
- если продолжает давать хорошие результаты, TTL можно автоматически продлевать еще на 24 часа;
- если перестал быть полезным, удалить после TTL.

Отклоненные предложения не предлагать повторно слишком часто. Сделай cooldown, например 7 дней.

Порог появления предложения сделай конфигурируемым.

Используй разумную эвристику, например частоту хэштега среди нескольких разных роликов и качество этих роликов.

## 6. Какие ролики подходят

Жесткие условия:

- возраст ролика <= 24 часов;
- минимум 10 000 просмотров;
- тематика связана с фильмами/сериалами;
- есть признаки русскоязычной аудитории;
- ролик еще не отправлялся конкретному пользователю.

Минимальный порог просмотров обязательно вынеси в конфиг.

Русскоязычность определяй по комбинации признаков:

- русский caption;
- русские хэштеги;
- русский текст/субтитры;
- русская речь.

Не требуется, чтобы присутствовали сразу все признаки.

Сделай функцию/модуль определения language relevance и возвращай confidence/score.

## 7. Мониторинг

Каждые 15 минут:

1. выполнить поиск по активным запросам;
2. получить кандидатов;
3. обновить текущие показатели;
4. записать snapshot статистики;
5. вычислить текущую скорость роста;
6. обновить Trend Score.

Для видео сохранять только необходимые метаданные и показатели.

Историю metric snapshots старше 48 часов автоматически удалять.

Не скачивать MP4 каждого кандидата.

MP4 скачивать только для финальных TOP-3 или когда он непосредственно нужен для отправки.

## 8. Реальная скорость роста

Главный показатель должен использовать разницу между несколькими наблюдениями.

Например:

`views_velocity = (current_views - previous_views) / elapsed_hours`

Аналогично можно считать:

- likes/hour;
- shares/hour;
- comments/hour.

Если видео найдено впервые и исторического snapshot еще нет, временно использовать приблизительный показатель:

`views / age_hours`

Но такой результат должен иметь меньшую уверенность, чем реальное измерение роста.

После второго snapshot автоматически перейти на реальную скорость.

Обработай:

- счетчики, которые временно уменьшились;
- пропавшее видео;
- дубли;
- очень маленький интервал между измерениями;
- нулевые значения;
- выбросы.

## 9. Trend Score

Не использовать просто абсолютное число просмотров.

Trend Score должен учитывать примерно:

- скорость прироста просмотров;
- скорость прироста лайков;
- share rate;
- comment rate;
- engagement;
- свежесть ролика;
- размер аудитории автора;
- breakout-эффект, когда маленький аккаунт внезапно получает большой охват.

Предлагаемый стартовый баланс:

- 40% — views velocity;
- 20% — likes velocity;
- 15% — share rate;
- 10% — comment rate;
- 10% — freshness;
- 5% — breakout относительно размера аккаунта.

Это стартовые веса, а не жесткое требование.

Вынеси веса в конфиг, чтобы их можно было менять без переписывания алгоритма.

Используй нормализацию, чтобы один огромный ролик не ломал весь ranking.

Подумай над log scaling / percentile normalization / clipping выбросов.

В коде подробно прокомментируй формулу.

## 10. Выбор TOP-3

Рассылка идет каждые 3 часа по фиксированному московскому времени.

Timezone:

`Europe/Moscow`

Расписание:

- 00:00
- 03:00
- 06:00
- 09:00
- 12:00
- 15:00
- 18:00
- 21:00

Перезапуск приложения не должен сдвигать расписание.

В каждый цикл выбрать 3 лучших доступных видео.

Если сильных видео меньше трех, добить подборку более слабыми подходящими кандидатами.

Если подходящих видео вообще нет, отправить подписчикам сообщение вроде:

`За последний цикл новых подходящих видео не найдено.`

Если разные TikTok используют одну и ту же сцену/фильм, это не проблема: все три можно отправить.

## 11. Защита от повторов

Одно и то же TikTok-видео не должно повторно отправляться одному и тому же пользователю.

Сделай отдельную таблицу deliveries, например:

- user_id;
- video_id;
- delivered_at;
- delivery_type.

Историю deliveries можно хранить минимум 30 дней.

После этого старые записи можно очищать.

Таким образом команда `/top` может отправить видео конкретному пользователю и не лишить остальных пользователей будущей общей рассылки.

## 12. Telegram authentication

Регистрации как таковой нет.

Любой Telegram-аккаунт может выполнить:

`/start`

Бот запрашивает общий пользовательский пароль.

Пароль задается через `.env`, например:

`USER_PASSWORD=...`

После правильного ввода Telegram user ID сохраняется в SQLite как авторизованный.

Авторизация должна переживать рестарты приложения.

Все обычные пользователи имеют одинаковые права.

Никаких user/admin ролей для обычных функций нет.

Не логировать пароль.

Использовать безопасное сравнение.

Добавить простой rate limit на неудачные попытки ввода пароля.

## 13. Telegram-команды

Реализовать:

`/start`
- авторизация по общему паролю.

`/status`
- авторизован ли пользователь;
- глобальное состояние сервиса;
- включена ли личная рассылка;
- время последнего TikTok scan;
- количество актуальных кандидатов;
- время следующей рассылки.

`/top`
- получить текущие лучшие ролики прямо сейчас;
- отправленные через `/top` видео записываются как доставленные этому конкретному пользователю;
- это не должно мешать отправить их другим пользователям.

`/pause`
- остановить автоматические рассылки только текущему пользователю;
- глобальный поиск продолжает работать.

`/resume`
- снова включить личную рассылку.

`/queries`
- показать базовые и текущие одобренные временные запросы.

`/logout`
- удалить авторизацию текущего Telegram ID.

## 14. Глобальное управление сервисом

Нужен отдельный пароль:

`ADMIN_PASSWORD=...`

Он не связан с обычным пользовательским паролем.

Команда:

`/stop_service`

После команды бот должен запросить ADMIN_PASSWORD.

При правильном пароле:

- остановить автоматический поиск TikTok;
- остановить scheduled broadcasts;
- не останавливать Telegram-бот;
- команды `/status`, `/start_service` и другие административные функции должны продолжить работать.

Состояние глобальной остановки хранить в БД, чтобы после restart VPS сервис не начал поиск автоматически, если ранее был остановлен вручную.

Команда:

`/start_service`

также требует ADMIN_PASSWORD и возвращает scanner + scheduler в работу.

`/status` показывает:

`🟢 сервис работает`

или

`🔴 поиск и рассылка глобально остановлены`

Не передавать пароль прямо аргументом команды, чтобы он не оставался очевидно в истории сообщений типа `/stop_service password`.

После команды бот должен перейти в состояние ожидания пароля с небольшим TTL.

## 15. Формат отправки

Пользователь должен получить:

1. MP4;
2. preview;
3. ссылку TikTok;
4. показатели;
5. Trend Score;
6. автора;
7. информацию об источнике фильма/сериала.

Telegram сам показывает preview для отправленного видео, поэтому можно использовать video message + caption, а если caption слишком большой — отдельное текстовое сообщение.

Пример:

🔥 Быстро растет

Источник: Бойцовский клуб
Уверенность: 84%

👁 Просмотры: 184 200
📈 Рост: +38 400 просмотров/ч
❤️ Лайки: 21 300
❤️ Рост лайков: +3 200/ч
🔁 Репосты: 2 140
💬 Комментарии: 760

🕐 Опубликовано: 4 ч 17 мин назад
👤 Автор: @username
👥 Подписчиков: 12 400

⭐ Trend Score: 87/100

🔗 Оригинал: <TikTok URL>

Если фильм определить не удалось:

`Источник: не удалось определить`

Если есть правдоподобный, но не полностью уверенный результат:

`Возможно: Бойцовский клуб`
`Уверенность: 65%`

Не придумывать источник при отсутствии доказательств.

## 16. Определение фильма/сериала

Название фильма или сериала достаточно.

Определение:

- серии;
- сезона;
- точного таймкода;

не является обязательным для MVP.

Если эти данные удается надежно получить практически бесплатно, можно показать их как bonus field, но не тратить на это значительные ресурсы и не усложнять MVP.

Реализовать source identification pipeline каскадом от дешевых методов к дорогим.

Пример:

### Stage 1
Caption + hashtags.

Попытаться найти название непосредственно в caption/hashtags.

### Stage 2
Доступные TikTok subtitles/captions.

### Stage 3
OCR.

Извлечь несколько репрезентативных кадров, а не анализировать каждую секунду.

Использовать бесплатный локальный OCR, например Tesseract или более подходящий легкий open-source вариант.

### Stage 4
Speech-to-text.

Только если предыдущие этапы не помогли.

Можно использовать Whisper/faster-whisper или другое бесплатное решение.

Учитывая 2 GB RAM:

- использовать маленькую модель;
- CPU-friendly quantization;
- запускать последовательно;
- не держать модель постоянно в памяти без необходимости;
- анализировать только TOP-кандидатов;
- предусмотреть timeout;
- не допускать OOM.

### Stage 5
Бесплатный web/search lookup.

Найденные:

- реплики;
- имена;
- текст с экрана;
- caption;
- hashtags

можно использовать для поиска вероятного фильма/сериала.

### Stage 6
Verification/normalization.

Можно использовать бесплатные внешние источники вроде TMDB либо другие актуальные бесплатные источники.

Сторонние сервисы разрешены, если:

- бесплатны;
- их использование легально и соответствует их условиям;
- они не являются обязательными;
- при отказе сервис не ломает остальной бот.

Сделай source identifier модульным.

Пример интерфейса:

`SourceIdentifier`

Результат:

- title;
- confidence;
- evidence;
- provider/method;
- optional year;
- optional type.

Пользователю отображать просто поле `Источник`, а не разделять обязательно фильм/сериал.

## 17. Когда выполнять тяжелое распознавание

Не запускать OCR/ASR/web-search для сотен кандидатов.

Для всех кандидатов:

- metadata;
- caption;
- hashtags;
- language relevance;
- metrics;
- ranking.

Тяжелое source identification выполнять преимущественно для финального TOP-3 перед рассылкой.

Допускается предварительный легкий source detection по caption/hashtags.

## 18. MP4 storage

MP4 скачивать только для роликов, которые собираемся отправить.

После скачивания:

- отправить пользователям;
- сохранить файл локально не больше 6 часов;
- затем удалить автоматически.

Приложение должно также чистить orphan/temp files после сбоев и restart.

Не хранить большую библиотеку TikTok-видео.

Если загрузка MP4 не удалась, не отменять весь цикл.

Отправить:

- ссылку;
- статистику;
- информацию об ошибке загрузки файла.

Не нужен PostgreSQL.

Продумай нормализованную, но простую схему.

Минимально нужны сущности примерно:

## 20. Очистка данных

Автоматически:

- metric snapshots >48h удалить;
- старые кандидаты, которые больше не нужны, удалить;
- deliveries старше примерно 30 дней можно удалить;
- динамические запросы чистить по TTL;
- MP4 старше 6 часов удалить;
- временные файлы удалить;
- лог-файлы ротировать.

Не удалять:

- список авторизованных пользователей;
- пользовательский `/pause`;
- глобальное состояние stopped/running.

Также:

- ranking weights;

Сделай адекватную validation конфигурации при запуске.

При отсутствии обязательного параметра приложение должно завершиться с понятной ошибкой.

## 22. Планировщик

Использовать timezone-aware scheduler.

Нужно избежать:

- двойной рассылки после restart;
- двух параллельных scan;
- нескольких одновременных broadcast;
- overlap тяжелых source identification задач.

Используй locks/state там, где необходимо.

Если scan длится больше 15 минут, новый параллельный scan не запускать.

Если сервер был выключен в 09:00 и включился в 10:00, не нужно обязательно отправлять пропущенную подборку 09:00.

Следующая обычная рассылка должна произойти в 12:00 MSK.

## 23. Ошибки внешних сервисов

Каждая внешняя операция должна иметь:

- timeout;
- retries с разумным backoff;
- обработку rate-limit;
- structured logging;
- отсутствие падения всего процесса.

Если TikTok provider временно недоступен:

- залогировать;
- `/status` должен это отражать;
- повторить на следующем scan;
- Telegram bot должен продолжать отвечать.

Если source identification сломался:

- всё равно отправить TikTok;
- написать `Источник: не удалось определить`.
